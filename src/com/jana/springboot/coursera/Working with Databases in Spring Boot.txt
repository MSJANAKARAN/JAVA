MySQL Database with Spring Boot
	Before connecting the application, a target database must be created via the terminal CLI using:
		CREATE DATABASE demoDB;
		USE demoDB;

	To establish a database connection, two critical dependencies must be declared in the Maven file:
		• spring-boot-starter-data-jpa: Pulls in Hibernate and Java Persistence API utilities for Object-Relational Mapping (ORM).
	
		• mysql-connector-java: The official database driver enabling communication with the MySQL engine. 
		It should be configured with its <scope> explicitly set to runtime.
		
	Application Properties Setup (application.properties)
		• spring.datasource.url: 
			Points to the localized network host address, passing the standard port and database identifier: jdbc:mysql://localhost:3306/demoDB.
		
		• spring.datasource.username / password: 
			Grants environment security access parameters (e.g., username set as root).
		
		• spring.jpa.hibernate.ddl-auto: 
			Configured to update. This ensures that Hibernate checks the database on boot, automatically creating missing tables or applying model alterations 
			without destroying or overwriting pre-existing data.
		
		• spring.jpa.show-sql: 
			Set to true to cleanly print all raw SQL commands generated by Hibernate directly into the runtime console.
		
		• Dialect Mapping: 
			Configured with MySQL8Dialect to tell Hibernate precisely how to translate Java actions into valid MySQL-compliant syntax commands.

Java Persistence API (JPA) and JPA Repositories:
	JPA Entities
		An entity is a POJO (Plain Old Java Object) class featuring attributes (properties) and behaviors (getters, setters, and constructors) that structurally 
		represents a table within a database. It directly maps its private fields to matching database table columns.

	JPA Repositories
		An interface provided by the Spring Data JPA framework to streamline database interactions.
		It inherits from the core framework repository using the Java extends keyword, declaring both the target Entity class and its Primary Key data type
		
			public interface UserRepository extends JpaRepository<User, Long> { }

	Built-in Repository Methods
		• save(entity): Saves a newly initialized record or updates an existing entity record in the database.
		
		• findById(id): Retrieves a highly specific, single entity row corresponding to the provided primary key.
		
		• findAll(): Fetches all database table rows at once and returns them as a structured list collection.
		
		• deleteById(id): Permanently removes a targeted entry matching the specific primary key.
		
		• Dynamic Property Lookups: Generates automated custom queries dynamically written based on method naming conventions (e.g., findByEmail(email)).

Hibernate ORM Framework
	Open-source Object-Relational Mapping (ORM) framework for Java that dynamically maps Java object structures directly onto relational database schemas.
	
	It completely abstracts the data layer, eliminating the need to write manual SQL queries for foundational operations.
	
	Key Performance Capabilities:
		• HQL (Hibernate Query Language): 
			An object-oriented variant of SQL that queries data models based on Java classes and attributes rather than physical database table and column names.
		
		• Caching & Lazy Loading: 
			Serves as critical performance optimization utilities (to be covered in depth in subsequent lessons).
		
		• Transaction Support: 
			Works natively with Spring's Transaction Control Language (TCL) architectures.

Advanced JPA Relationships
	1. One-to-Many Relationship Setup
		• Core Example: An Author can write multiple books, establishing a relationship where one parent entity links to multiple child entities.
		
		• The Parent Side (Author.java):
			
			• Declares a collection field (List<Book> books).
			
			• Annotated with @OneToMany using the mappedBy = "author" parameter, which designates the Book class as the owning side that defines the relationship.
			
			• Employs cascade = CascadeType.ALL, meaning any structural modifications (like deletions or updates) performed on the author automatically trickle down 
				and update the associated books.
		
		• The Child/Owning Side (Book.java):
			
			• Declares a single parent reference property (Author author).
			
			• Annotated with @ManyToOne, mapping the object link back to the author table.
			
			• Uses @JoinColumn(name = "author_id") to explicitly define the physical Foreign Key column name within the underlying database table layout.
			
	2. Many-to-Many Relationship Setup
		• Core Example: Multiple Students can enroll in multiple Courses (and vice versa), forming an multi-directional data web. If there are N students and M courses, 
			up to N × M structural relationship mappings can exist.

		• The Owning Side (Student.java):
			• Annotated with @ManyToMany.
			
			• Utilises the @JoinTable annotation to dynamically generate a brand new intermediate bridge table named student_course in the database.
			
			• The bridge table automatically merges two distinct Foreign Key columns using explicit mapping properties: joinColumns = @JoinColumn(name = "student_id") 
				(pointing back to the student primary key) and inverseJoinColumns = @JoinColumn(name = "course_id") (pointing forward to the course primary key).
		
		• The Inverse Side (Course.java):
			• Maintains a collection block (Set<Student> students) to map structural entities cleanly.
			
			• Annotated with @ManyToMany(mappedBy = "courses"), which establishes a mirrored relationship and points back to the definition setup inside the Student class.
	
	
	@JoinColumn (The Owning Side):
		• Explicitly placed on the owning side of a relationship.
		
		• Defines the actual physical Foreign Key column name within the underlying database schema that joins two tables 
			(e.g., creating an author_id column inside the book table).

	mappedBy (The Inverse / Non-Owning Side):
		• Configured strictly on the inverse (non-owning) side of a data relationship.
		
		• Directs the framework back to the property name on the owning entity that manages the relationship 
			(e.g., mappedBy = "author" inside the Author class points directly to the author field declared in the Book class).
		
		• Helps prevent redundant join columns or duplicate bridge setups in the database.

	Golden Rules & Best Practices
		• Always use Bidirectional over Unidirectional @OneToMany: 
			A purely unidirectional @OneToMany setup (without @ManyToOne on the child) forces Hibernate to generate an extra join table or execute inefficient UPDATE SQL commands.
		• Keep both sides in sync: 
			When writing Java code, always update both sides of the relationship using helper methods (like addEmployee()) to avoid inconsistent states before persisting.
	
	Example:
	Department.java One to Many
		import jakarta.persistence.*;
		import java.util.ArrayList;
		import java.util.List;
		
		@Entity
		@Table(name = "departments")
		public class Department {
		
		    @Id
		    @GeneratedValue(strategy = GenerationType.IDENTITY)
		    private Long id;
		
		    private String name;
		
		    // 'mappedBy' tells Hibernate to look at the 'department' field in the Employee class
		    @OneToMany(mappedBy = "department", cascade = CascadeType.ALL, orphanRemoval = true)
		    private List<Employee> employees = new ArrayList<>();
		
		    // Synchronisation Helper Methods (Best Practice)
		    public void addEmployee(Employee employee) {
		        employees.add(employee);
		        employee.setDepartment(this);
		    }
		
		    public void removeEmployee(Employee employee) {
		        employees.remove(employee);
		        employee.setDepartment(null);
		    }
		
		    // Constructors, Getters, and Setters
		}

	Employee.java Manu to One
		import jakarta.persistence.*;
		
		@Entity
		@Table(name = "employees")
		public class Employee {
		
		    @Id
		    @GeneratedValue(strategy = GenerationType.IDENTITY)
		    private Long id;
		
		    private String name;
		
		    @ManyToOne(fetch = FetchType.LAZY) // Best practice: Always lazy load to prevent N+1 issues
		    @JoinColumn(name = "department_id") // Specifies the Foreign Key column in 'employees' table
		    private Department department;
		
		    // Constructors, Getters, and Setters
		}

	Lazy Loading vs. Eager Loading Strategies in JPA and Spring Boot
		• Eager Loading (FetchType.EAGER):
			• Function: Automatically pulls the parent entity along with all associated child relationships immediately inside the initial database query.
			
			• Trade-off: Convenient for immediate access, but creates severe performance bottlenecks and memory strain when operating on massive data collections.
		• Lazy Loading (FetchType.LAZY):
			• Function: Fetches only the targeted parent record initially. The connected child data collections are completely deferred and only query the 
			database on-demand when an explicit getter method is invoked in the code.
			
			• Trade-off: Highly optimized for performance, but can trigger session timeouts or scope exceptions if child data is requested after active transaction context closes.
			
		Example:
			@OneToMany(mappedBy = "author", cascade = CascadeType.ALL, fetch = FetchType.LAZY)
			private List<Book> books;

	Java Persistence Query Language (JPQL)
		Acts as an object-oriented upgrade to SQL designed specifically for JPA frameworks.
		While standard SQL operates directly on physical database tables and columns, JPQL operates entirely on your Java application's 
		domain model—specifically its @Entity classes and private field attributes.
		
		SQL:
			SELECT * FROM employee_table WHERE employee_name = 'John';
		JPQL:
			@Query("SELECT e FROM Employee e WHERE e.name = :name")
			List<Employee> findByName(String name);

	Pagination and Sorting:
		Pagination and sorting are vital built-in features of Spring Data JPA used to optimize performance and prevent network lag 
		when handling large corporate datasets on visual dashboards.

		    Pageable pageable = PageRequest.of("0", "5", sort);
			userService.registeredUsers(pageable);

Field Level Validation
	Validations are natively triggered on method parameters inside controllers, operating in combination with data binding annotations 
	like @RequestBody (for JSON payloads) or @ModelAttribute (for HTML form views).

	Annotations for field level validation
		• @NotNull: Mandates that a targeted field value must not be null.
	
		• @NotBlank: Explicitly used on String attributes to declare that the field is strictly mandatory and cannot be empty or consist solely of whitespace.
	
		• @Size: Imposes exact string length constraints, defining how small or large a textual input can be using explicit minimum and maximum boundaries.
	
		• @Email: Automatically checks incoming strings against global email structures to enforce a valid layout (e.g., verifying it contains the @ annotation symbol).
	
		• @Min / @Max: Restricts numerical inputs to defined floors or ceilings. The text sets a custom threshold example: @Min(value = 18, message = "Age must be 18 or above").
	
		• @Pattern: Enforces advanced validation criteria (like complex user password strengths) by ensuring the input string perfectly matches a custom Regular Expression (Regex).

	Error Capture
		@Valid: Placed directly on the controller's incoming method parameter to act as a system trigger. 
		It forces Spring to evaluate all constraint annotations defined inside the target object before running the method body logic.

Global Exception Handling
	@ControllerAdvice is a specialized, global component annotation that centralises error handling across the entire application footprint.
	
	ResponseEntityExceptionHandler
		This is a predefined base class provided by Spring that acts as a convenient, foundational safety net for catching standard web errors.
		
		• MethodArgumentNotValidException (triggered when request payload structural inputs fail validation rules).
		
		• HttpRequestMethodNotSupportedException (triggered when an invalid HTTP verb calls a target endpoint).

	• @ExceptionHandler: Configured inside the advisory class to map specific target Java exception classes to concrete, automated handler methods.
	
	• ResponseEntity: Represents the entire output HTTP framework envelope. It allows developers to completely customize and package structured metadata—overriding 
		raw HTTP Status Codes, custom error messages, and payload headers—before returning data to the client.
	
	• @ResponseStatus: Directly ties specific HTTP response codes to concrete exception scenarios.

	Implementation Steps for Developers
		1. Create the Advisor Class: 
			Establish a core global handler class (e.g., GlobalExceptionHandler) marked with @ControllerAdvice that extends the base ResponseEntityExceptionHandler.
		
		2. Override Framework Exceptions: 
			Implement customized handler methods for standard web routing exceptions using clean overriding methods.
		
		3. Build Custom Exceptions: 
			Construct application-specific, custom Java exception classes to handle precise domain layer logic failures.
		
		4. Return Structured Responses: 
			Package error properties into a uniform error response model (e.g., an ErrorResponse object mapping a custom error code and a human-readable message string) 
			wrapped inside a customized ResponseEntity to give testing developers immediate troubleshooting clarity.
